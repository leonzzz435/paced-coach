## Live Astra lifecycle

The live test used a separate local PostgreSQL database, Redis instance, API and
worker. It used an existing OpenAI credential but no real athlete data. Tracing
was disabled. The synthetic athlete declared four runs a week, weekday limits,
three unavailable days and a half-marathon goal.

Observed so far:

1. Profile and competition were entered and saved through the real browser UI.
2. The coach asked whether race Sunday was an exception to the ordinary
   40-minute Sunday limit.
3. API and worker were stopped and recreated while the job awaited an answer.
4. The same clarification remained available. An answer submitted through the
   browser resumed the same job.
5. The job completed and published schema-v3 season and execution plans.
6. The plan contained 28 consecutive days. All daily durations respected the
   declared limits; Tuesday, Thursday and Friday had no sessions.
7. The generated plan rendered in the real UI without captured JavaScript errors.
8. A proposed Wednesday reduction left version 1 and the 40-minute day unchanged
   until acceptance. Accepting saved version 2 with 25 minutes on that day only;
   the other 27 days and season roadmap were unchanged.
9. A second proposed change was rejected through the browser. The complete active
   plan response remained identical before and after rejection.
10. After fixing the response-envelope tool limit, live memory-model requests
    completed without the earlier limiter exception.

The live pass exposed and fixed two runtime defects: structured answer envelopes
incorrectly consumed zero-tool budgets, and untyped JSON metadata prevented
proposal acceptance on asyncpg. Regression tests now exercise the real agent
framework and PostgreSQL boundary. Public demo checks also caught legacy device
metrics, eager local-app navigation and persistence actions in the preview;
the updated browser tests and guarded capture verify their removal.

This is one observed scenario, not a coaching-quality benchmark. Cost and token
measurements were not established for the LangGraph run; no cost reduction or
model-superiority claim is made. The separate Agents API smoke test does not
replace application acceptance testing.

## Bounded model comparison

The same synthetic 181-token constraint prompt was sent once to each model via
the application's model selector, with medium reasoning and research disabled.
Both models asked about a race-day exception, stayed within the stated weekly
availability, and avoided invented wearable measurements or claims of saving a
plan. GPT-5.5 returned in 10.82 seconds with 686 output tokens (404 reasoning);
Astra returned in 17.16 seconds with 478 output tokens (254 reasoning).

This was one standalone prompt per model, outside the full coaching workflow.
It does not establish relative quality, typical latency, or cost. The full live
application lifecycle above used Astra; an equivalent GPT-5.5 lifecycle was not
run as part of this comparison.
